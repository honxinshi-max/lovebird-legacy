# 牡丹鹦鹉育种社会：首个可玩繁育垂直切片设计

状态：待用户复核  
日期：2026-08-29  
项目根目录：`/Users/hyc/Projects/lovebird-breeding-society`

## 1. 决策摘要

第一步制作一个本地运行的 2D 网页垂直切片，验证以下核心玩家循环：

> 研究种鸟 → 比较配对 → 承担风险并繁育 → 解释幼鸟的基因与血统 → 按多种价值路线留鸟 → 开始第二代繁育

这一步不试图实现完整经营社交平台。它优先证明三件事：

1. 确定性程序能够产生可复现、可解释且仍有不确定感的遗传结果。
2. 玩家选择配对时必须面对真实取舍，不能沿着单一总分寻找“神鸟”。
3. 每只鸟的身份、父母、祖源、基因、表型和经历能够作为永久记录延续到下一代。

## 3. 成功定义

### 3.1 玩家层成功

一次完整试玩应允许玩家在 15–25 分钟内：

1. 认识 6 只初始种鸟。
2. 比较至少 3 组候选配对。
3. 完成一次繁育并查看 3 只同窝幼鸟。
4. 解释其中至少两只幼鸟在羽色、性能、健康风险或性格潜力上的差异来源。
5. 选择一只幼鸟留作下一代，并完成第二次配种。

核心质性门槛：玩家能够说出至少一个不依赖“综合数值最高”的留鸟理由。

### 3.2 系统层成功

- 相同存档、相同父母和相同繁育事件种子必须重放出完全相同的幼鸟。
- 任意鸟均有唯一 `Bird_ID`；正式登记鸟另有不可变的 `Band_ID`。
- 亲子关系、祖源比例、事件历史和原始繁育者不可被普通状态更新覆盖。
- 繁育结果不能绕过物种兼容、性别、年龄、健康和繁育次数约束。
- 所有性能优势至少连接一个机会成本或资源竞争关系。
- 界面不显示综合战力、综合品质或自动推荐的唯一最佳配对。

## 4. 首版内容边界

### 4.1 纳入

- 单玩家、本地存档、无需登录。
- 桃脸、费氏、面具 3 个基础物种。
- 6 只固定但基因不同的成年初始种鸟。
- 12 个离散基因位点：羽色 4、花纹 2、眼色 1、脸型 1、羽型 1、健康风险 3。
- 6 个多基因性能组：速度、爆发力、耐力、灵活度、召回潜力、学习潜力。
- 5 个性格倾向：乖巧、胆量、稳定、警觉、亲和潜力。
- 物种兼容、显隐性、基因重组、小概率突变、遗传稳定度、近交与隐性健康风险。
- 鸟舍、配对实验室、出生揭晓、鸟只档案、四代可视血统和第二代目标。
- 参数化分层 SVG 鸟形象及少量关键帧待机动画。
- 本地行为事件账本，用于试玩复盘，不上传外部服务。

### 4.2 明确延期

- 金币发行、充值、玩家市场、借种费和交易手续费。
- Club、好友、聊天、全服任务和公开展示。
- 手养、训练、疾病治疗、逃跑、猎人和失踪找回事件。
- 比赛、摄影导出、付费装饰和 4K 输出。
- 官方新品种申请、人工审核和正式品种数据库写入。
- 实时 AI 生成、AI 自动学习新品种和开放式文本生成。

这些系统保留在长期愿景中，但首个切片不会预留空按钮或伪功能。

## 5. 玩家流程

### 5.1 鸟舍

玩家首先看到 6 张种鸟卡片。卡片只展示作决策所需的摘要：物种、性别、年龄、两项突出特征、一项明显代价、健康状态和繁育资格。

玩家可进入鸟只档案查看更深信息，但不能看到隐藏的完整基因真值。首版采用三层信息：

- 已知：可直接观察的表型、父母、物种、历史。
- 检测：已揭示的基因位点和携带状态。
- 未知：尚未检测或只能由后代反推的位点。

初始种鸟提供足以完成第一轮决策的部分检测结果，保留少量未知携带状态。

### 5.2 配对实验室

玩家选择一公一母后，系统显示：

- 生殖兼容等级及原因。
- 已知共同祖先、亲缘类别和近交风险区间。
- 可能出现的表型，不显示精确概率小数到误导性程度。
- 可能保留或损失的优势组合。
- 隐性健康风险提示。
- 双方剩余繁育次数和冷却状态。

系统不提供“最佳配对”按钮。风险提示解释信息，不替玩家作出价值选择。

### 5.3 出生揭晓

一次繁育产生固定 3 只同窝幼鸟，以便玩家比较同一父母下的重组差异。揭晓顺序为：

1. 形象与名字占位。
2. 父母和祖源。
3. 可见表型。
4. 性能及性格潜力区间。
5. 已知健康结果。
6. “为什么会这样”的遗传解释卡。

解释卡必须引用具体来源，例如“从父亲获得浅色隐性等位基因，从母亲获得相同隐性等位基因，因此表现为浅色眼睛”，不能只写“随机获得”。

### 5.4 留鸟与第二代

玩家为 3 只幼鸟分别标记一个候选方向：竞技、外貌、亲和、健康种群或稀有基因保留。方向只是玩家标签，不改变数据。

时间推进仅用于让所选幼鸟达到首版演示繁育年龄，不模拟完整成长过程。玩家随后用该鸟与另一只无近亲种鸟完成第二次配种，闭合两代循环。

## 6. 规则模型

### 6.1 确定性随机

所有看似随机的结果由可播种伪随机数生成器产生。每次繁育事件保存：

- `save_id`
- `breeding_event_id`
- 父母 `Bird_ID`
- 规则版本
- 事件种子
- 生成结果摘要哈希

事件种子在幼鸟出生后进入历史记录。这样可以重放和审计，同时避免配种前直接向玩家泄露结果。离线原型不以此机制防作弊；未来联网版本再由服务器持有不可预知种子。

### 6.2 物种兼容

首版兼容矩阵是游戏规则配置，不宣称等同于现实动物医学结论：

| 配对 | 兼容等级 | 首版效果 |
|---|---|---|
| 同物种 | 高度兼容 | 正常繁育成功率与基础健康风险 |
| 费氏 × 面具 | 有限兼容 | 较低成功率、后代遗传稳定度下降 |
| 桃脸 × 费氏 | 低兼容 | 明显降低成功率，并增加繁殖力不确定性 |
| 桃脸 × 面具 | 低兼容 | 明显降低成功率，并增加繁殖力不确定性 |

首版 3 个物种中没有“不兼容”组合，但规则引擎和配置枚举必须支持该状态，便于未来加入其他物种。

### 6.3 离散基因位点

每个位点保存来自父系与母系的两个等位基因，并定义：

- 显隐性或共显性关系。
- 表型映射。
- 是否与其他位点连锁。
- 重组概率。
- 突变目标和突变率。
- 物种内表达修饰。
- 健康影响及严重度。

健康位点区分携带、轻度功能影响和严重遗传缺陷。严重痛苦性疾病只作为需要避免的健康风险，不提供收藏加成、成就或比赛优势。

### 6.4 多基因性能与性格潜力

每项性能由多个小效应等位值、物种基础倾向和少量基因互作共同决定。基因给出潜力区间，而不是当前训练成绩。

计算次序固定为：

1. 继承父母的多基因单元。
2. 应用物种基础倾向。
3. 应用已定义的基因互作。
4. 应用遗传稳定度对应的重组保真机制。
5. 应用可重放的发育波动。
6. 计算资源竞争和机会成本。
7. 输出潜力区间与解释项。

不直接采用父母平均值，也不允许任意噪声覆盖遗传来源。

### 6.5 遗传稳定度

“稳定度 30%”被解释为目标优势基因块以较完整组合传递的概率，而不是幼鸟只继承父母 30% 的属性。

每个物种针对性状组配置三个结果带：

- 完整保留：核心优势基因块基本保持。
- 部分重组：保留部分贡献，组合被打散。
- 明显退化或小概率新组合：发生不利重组，或极低概率得到更有利组合。

每次结果都由实际继承的基因单元生成，稳定度只影响组合保留方式，不能直接给最终属性乘百分比。

### 6.6 Trade-off 与“禁止神鸟”

首版使用 4 条可解释的资源轴约束，不设置单一总属性预算：

- 爆发能量分配：速度与爆发提高会压缩长时耐力收益。
- 飞行形态：极端体型或长尾能提升外貌稀有性，但会增加灵活或持续飞行代价。
- 神经反应：高警觉有助竞技反应，却降低乖巧与陌生环境稳定性。
- 社会依附：极高温顺与亲和潜力有利手养，却不会同时获得最高独立探索和竞赛反应。

单项潜力允许出现优秀值，但所有维度同时接近上限在规则上不可达。系统不计算或展示把这些维度重新合成的总分。

### 6.7 祖源、亲缘和近交

- 纯种初始鸟的祖源为对应物种 100%。
- 幼鸟祖源取父母祖源向量各 50%，再归一化并保留足够精度。
- 祖源接近纯种不自动获得官方纯种或官方品种身份。
- 界面展示四代血统，但数据层保留所有可达祖先关系。
- 亲缘计算使用共同祖先路径，不以相同物种或相同品系代替血缘关系。
- 近交风险综合亲缘系数、已知共同隐性风险位点和未检测不确定性，不采用“近亲必然畸形”的固定判定。

## 7. 核心数据模型

### 7.1 Bird

不可变身份字段：

- `birdId`
- `bandId`
- `birthDate`
- `birthPlayerId`
- `fatherId`
- `motherId`
- `speciesAtBirth`
- `genome`
- `ancestryComposition`
- `rulesetVersion`

可变状态字段：

- 名字
- 当前主人
- 当前健康状态
- 当前生命周期阶段
- 繁育次数、冷却和是否允许繁育
- 玩家添加的候选方向标签

派生字段不直接保存为权威真值，包括表型摘要、潜力区间、亲缘描述和可参赛资格；它们由版本化规则重新计算。

### 7.2 Genome

`Genome` 包含离散位点、父母来源标记、多基因单元、突变记录和检测可见性。每个幼鸟的基因都能追溯到父系、母系或新突变。

### 7.3 BirdEvent

历史采用只追加事件：出生、登记、繁育、健康限制、主人变更和玩家标签。首版只启用出生、登记、繁育和标签事件，但事件枚举允许未来扩展。

普通界面操作不能编辑或删除历史事件。修复损坏存档时只能从有效快照恢复，不能静默重写血统。

### 7.4 BreedingEvent

繁育事件保存父母、兼容结果、亲缘快照、风险快照、规则版本、种子、幼鸟列表及失败原因。失败的繁育尝试也保留事件记录，避免繁育次数和结果不一致。

## 8. 软件架构

首版采用无后端的模块化网页应用：

```text
React UI
  ↓ commands / view models
Application layer
  ↓ domain operations
Pure TypeScript domain
  ├─ genetics
  ├─ breeding eligibility
  ├─ kinship and pedigree
  ├─ phenotype and trade-offs
  └─ immutable history
  ↓ repository interfaces
IndexedDB persistence + seed fixtures
```

### 8.1 模块边界

- `domain/genetics`：基因继承、重组、突变、表达和解释。
- `domain/breeding`：资格、兼容、事件生成和同窝幼鸟。
- `domain/pedigree`：祖先图、亲缘类型、共同祖先和近交风险。
- `domain/phenotype`：将基因型映射为外观参数和潜力区间。
- `domain/history`：只追加事件及不变量校验。
- `application`：把一个玩家操作组织成事务，不包含遗传公式。
- `persistence`：IndexedDB 实现与内存测试实现。
- `ui`：页面和交互，只消费视图模型。
- `rendering`：SVG 图层组合，不反向修改鸟只数据。

领域层不得依赖 React、浏览器存储或网络，因此遗传和亲缘规则可独立测试，也能在未来迁移到服务端。

### 8.2 状态与存档

- 首次进入创建带固定规则版本的演示存档。
- 每个应用命令先通过领域校验，再以单次事务写入事件和最新快照。
- 自动保存只保存已完成命令，不保存一半生成的幼鸟。
- 导入导出不是首版玩家功能，但开发验证可以读取固定 JSON fixture。

## 9. 2D 表现

鸟形象使用统一 SVG 骨架和参数化图层：身体、头、脸罩、翅膀、尾羽、眼睛、喙、脚和花纹遮罩。

基因只输出受控参数：

- 调色板 token，而不是任意颜色字符串。
- 体型、头型和尾羽的离散轮廓级别。
- 预定义花纹遮罩和对称性参数。
- 眼色和喙色。
- 少量允许叠加的特殊特征。

首版动画仅包含呼吸、眨眼和歪头，所有鸟共享关键帧。配种结果不会生成新图片文件，每只鸟由数据实时组合。

## 10. 异常处理与安全边界

| 情况 | 系统行为 |
|---|---|
| 性别、年龄、健康或冷却不符合 | 禁止提交并解释具体条件 |
| 物种不兼容 | 禁止繁育，不消耗繁育次数 |
| 低兼容繁育失败 | 记录失败事件；是否消耗次数由统一规则决定，首版设为不消耗一生次数但进入短冷却 |
| 父母或祖先记录缺失 | 阻止该配对，不把“未知”当作“无近亲风险” |
| 存档规则版本不同 | 使用存档版本重放；不以新规则静默改写旧鸟 |
| 结果哈希不匹配 | 标记存档完整性错误并停止继续繁育 |
| IndexedDB 写入失败 | 不更新界面权威状态，提示重试；不得显示未持久化幼鸟 |
| 严重健康缺陷 | 明确标记健康和繁育限制，不提供正向奖励 |

## 11. 验收与验证

### 11.1 单元与属性不变量

- 每个位点的幼鸟等位基因只能来自父、母或显式突变记录。
- 祖源比例之和始终为 100%，不出现负数。
- 相同种子重放结果完全一致；不同繁育事件不能复用同一事件 ID。
- 任何鸟不能成为自己的祖先。
- 任何配对的共同祖先和亲缘类别在父母顺序互换时一致。
- 全同胞、半同胞、父女、母子、祖孙和无已知亲缘 fixture 均得到预期结果。
- 严重健康风险不会产生竞技或收藏奖励。
- 生成至少 10,000 窝后，不存在所有性能和性格维度同时位于最高档的个体。
- 低兼容不能被普通 UI 命令提升为高度兼容。

### 11.2 场景测试

1. 新建演示存档并浏览全部 6 只种鸟。
2. 完成同物种配对，验证 3 只幼鸟存在可解释差异。
3. 完成有限兼容配对，验证兼容代价进入结果与解释。
4. 尝试近亲配对，验证共同祖先和隐性风险提示。
5. 保留一只幼鸟并完成第二代配种。
6. 刷新浏览器，验证鸟只、血统和事件历史仍在。
7. 使用固定 fixture 重放，验证结果哈希一致。

### 11.3 可用性与视觉验证

- 1440×900 桌面和 1024×768 平板视口均能完成主循环。
- 关键操作不依赖 hover。
- 羽色不是风险和状态的唯一编码方式。
- 鸟只卡片、配对对比、血统图和出生揭晓没有文字遮挡或溢出。
- 使用浏览器完成实际点击路径、控制台错误检查和截图复核。

### 11.4 反馈指标

本地事件只记录产品行为，不记录隐私信息：

- 查看过多少只鸟的详细档案。
- 比较过多少组配对。
- 是否展开遗传解释。
- 每只幼鸟被标记的候选方向。
- 最终保留哪只鸟以及玩家选择的结构化理由。
- 是否完成第二代繁育。

原型通过的最低反馈证据是：至少 5 名目标试玩者中，4 名能完成两代闭环；至少 3 名给出不同的、非总分式留鸟理由。这只是首轮产品证据，不等于市场适配或商业发行批准。

## 12. 实施顺序

1. 建立领域类型、规则配置、种子随机和固定 fixture。
2. 以测试驱动完成遗传、兼容、亲缘、近交和 Trade-off 不变量。
3. 建立只追加事件、IndexedDB 仓储和演示存档。
4. 完成鸟舍、鸟档案和配对实验室。
5. 完成出生揭晓、遗传解释和留鸟选择。
6. 完成第二代时间推进与闭环。
7. 接入分层 SVG 外观和三种共享待机动画。
8. 运行单元、场景、属性不变量、浏览器和视觉验证。

## 13. 非目标与升级门

首个切片完成不自动授权继续制作社交、经济或正式新品种系统。只有同时满足以下条件，才讨论下一阶段：

- 技术验收全部通过。
- 目标试玩者能理解核心遗传解释。
- 留鸟理由没有收敛成单一最高分。
- 玩家愿意主动开始第二代繁育。
- 参数化外观足以让同窝幼鸟被辨认为不同个体。

下一阶段候选是“手养与训练如何改变表现但不改变 DNA”，而不是直接上线玩家市场或 Club。

## 14. 已批准与当前假设

已批准：采用第 2 路线，即可玩繁育垂直切片。

为避免小步骤反复确认，本设计作出以下可回滚假设：

- 首版采用本地网页，而不是原生移动应用。
- 首版界面语言为简体中文。
- 首版没有联网账号与真实支付。
- 现实物种兼容和遗传参数在原型中是可配置游戏规则；正式内容发布前需要鸟类遗传与福利专业复核。
- 设计规格批准后才进入实施计划和业务代码。
